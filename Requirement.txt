==================================================
I. CORE DESIGN PRINCIPLES
==================================================

Hãy tuân thủ các nguyên tắc sau.

### 1. API chính phải là scope-based using API

Developer-facing API ưu tiên:

using (Perf.Measure("Login"))
{
    await LoginAsync();
}

hoặc:

using (Perf.Measure())
{
    DoSomething();
}

Có thể hỗ trợ:

using var scope = Perf.Measure("Login");

nhưng block-based using phải là API documentation/recommended usage chính.

KHÔNG sử dụng:

Perf.Start("Login");
...
Perf.Stop("Login");

làm API chính.

Lý do:

- exception-safe;
- early return-safe;
- nesting tự nhiên;
- async-friendly;
- lifecycle rõ ràng;
- compiler đảm bảo Dispose;
- developer nhìn code là biết measurement boundary nằm ở đâu.

Perf.Measure() phải trả về một struct/class scope disposable phù hợp với mục tiêu zero/minimal allocation.

Ưu tiên:

ref struct nếu phù hợp với constraint thực tế.

Nếu ref struct không phù hợp với async hoặc required lifecycle, thiết kế một abstraction khác phù hợp.

Không được hy sinh async correctness chỉ để đạt zero allocation.

==================================================
III. MOST IMPORTANT FEATURE:
OUTER SCOPE + AUTOMATIC INNER MAPPING
==================================================

Đây là requirement quan trọng nhất.

Ví dụ developer viết:

using (Perf.Measure("Player:GetPlayer"))
{
    await GetPlayer();
}

Framework KHÔNG được chỉ trả về:

Player:GetPlayer = 47ms

Framework phải có khả năng tự tạo hierarchical trace:

Player:GetPlayer       47.82 ms
├── GetPlayer           45.21 ms
│   ├── SQL              31.42 ms
│   ├── Deserialize       2.17 ms
│   ├── InventoryService  11.86 ms
│   └── Redis              3.41 ms
└── ...

Developer không cần viết:

using (Perf.Measure("SQL"))
{
    ...
}

cho từng operation nếu adapter/instrumentation đã có khả năng tự phát hiện.

Mục tiêu:

ONE OUTER WRAPPER
        ↓
AUTOMATIC INNER INSTRUMENTATION
        ↓
HIERARCHICAL PERFORMANCE TREE

Không được tự động thêm:

DI container
event bus
message broker
database
distributed storage
web dashboard
distributed tracing backend

nếu chưa cần.

Core phải nhỏ.

Mỗi dependency phải có lý do.

==================================================
XLI. IMPORTANT: DO NOT FAKE CAPABILITIES
==================================================

Nếu platform/runtime không cho phép đo chính xác:

- CPU time
- lock wait
- allocation
- GC
- network throughput

thì phải:

1. phát hiện limitation;
2. ghi rõ limitation;
3. cung cấp best-effort implementation;
4. không giả mạo số liệu.

==================================================
XLII. DOCUMENTATION STYLE
==================================================

Documentation phải giải thích từ:

WHY

→ WHAT

→ HOW

→ INTERNAL IMPLEMENTATION

→ PERFORMANCE COST

→ LIMITATIONS

Ví dụ phải giải thích:

Tại sao AsyncLocal?

Tại sao không ThreadLocal?

Tại sao Source Generator?

Tại sao không Reflection?

Tại sao OperationId thay vì string?

Tại sao using?

Tại sao Histogram?

==================================================
XLIII. DEVELOPMENT RULE
==================================================

Trước khi viết code:

1. Inspect repository hiện tại.
2. Nếu repository đã có code, không overwrite bừa.
3. Xác định target frameworks.
4. Xác định Unity version nếu có.
5. Kiểm tra package dependencies.
6. Xác định build constraints.
7. Tạo architecture document.
8. Tạo implementation plan.
9. Sau đó mới implement.

Không hỏi tôi những câu hỏi không cần thiết.

Nếu có ambiguity:

- chọn phương án architecture hợp lý nhất;
- ghi lại assumption;
- tiếp tục implement.

Chỉ hỏi tôi khi ambiguity có thể làm thay đổi fundamental architecture.

==================================================
XLIV. QUALITY BAR
==================================================

Code phải đạt mức production-quality.

Yêu cầu:

- clean architecture;
- SOLID nhưng không overengineer;
- thread-safe;
- async-safe;
- low allocation;
- AOT-friendly;
- testable;
- extensible;
- observable;
- benchmarked.

Không viết code demo throwaway.

PERF CORE

Thiết kế và implement contract chính:

Perf.Measure()
PerfScope
PerfContext
PerfSpan
OperationId
ParentSpanId
Async context
Clock
Recorder

Mục tiêu đầu tiên:

Code:

using (Perf.Measure("Root"))
{
    using (Perf.Measure("Child"))
    {
        DoWork();
    }
}

phải tạo được:

Root
└── Child

với:

TraceId
SpanId
ParentSpanId
OperationId
Start
End
Duration
Status

Sau đó chứng minh:

using (Perf.Measure("Root"))
{
    await Task.Delay(100);

    await SomeAsyncOperation();
}

vẫn giữ đúng hierarchy sau await/thread switch.

Sau khi Core pass tests, mới tiếp tục phase tiếp theo.

==================================================
XLVII. MOST IMPORTANT API CONTRACT
==================================================

API cuối cùng phải hướng tới trải nghiệm:

using (Perf.Measure("Player:GetPlayer"))
{
    await GetPlayerAsync();
}

Developer chỉ định:

"đây là boundary tôi muốn đo"

Framework chịu trách nhiệm:

"bên trong boundary này đã xảy ra những operation gì và mỗi operation tốn bao nhiêu."

Đây là nguyên tắc kiến trúc cốt lõi của toàn bộ project.

Bắt đầu bằng việc inspect repository và lập architecture proposal.
